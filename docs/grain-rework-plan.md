# 颗粒重构计划（Grain Rework Plan）

> 状态：**P1b、P1、P0、P2 已完成（v0.4.51）；P3′/P4′ 经实测判定不可行；待办：每胶卷 density_curves 接线**
> 范围：颗粒（film grain）的观感、一致性、性能；P1b 为导出末端色彩空间修复
> 不涉及：LUT / DIR / CMY / morph / 黑位管线
> 定案日期：2026-10-27（P1b 完成于 2026-10-27）

---

## 1. 定案结论

**全程 CPU 实现，保持 OpenGL 3.3 最低要求，不做 GL 4.3 compute，不做 P5 film-fixed。**

理由（基于实测与用户约束）：

| 判据 | 结论 |
|---|---|
| 用户工作流 | 只出全分辨率或 80% 分辨率（单一尺寸），不比对跨尺寸颗粒 → film-fixed 价值≈0 |
| 导出耗时容忍 | ≤ 10 s；CPU 64 MP 实测增量 0.6–1.1 s，余量约 10× |
| 滑块响应容忍 | ≤ 1 s；CPU 4K 视口重算 40–110 ms，余量约 9–25× |
| GPU 独有收益 | 仅"4K@60fps 每帧重算颗粒"与"拖动尺寸滑块即时跟手"，对静帧修图无价值 |
| GPU 的隐性成本 | 需 4.3（RDP/虚拟机/虚拟显示适配器不可用）+ 双实现 → 重现"预览/导出一致性"问题 |

**CPU 路线的额外收益**：预览、导出、缩略图共用同一份实现，一致性由构造保证，不需要对齐工作。

## 5. 每项改动的原因

**P0 标定** —— 现状所有参数都是手调的，没有参照值。物理参考给出 σ(D)、频谱/团簇、偏度三条可测曲线，让"改好了没有"可判定。历史上"移植了参数没移植算法"正是缺这一步。

**P1 统一 + 保护** —— 预览与导出是两套实现，归一化不同导致导出强 45%；且导出尺度依赖输出尺寸，小尺寸会退化。两者都是确定性缺陷，不需要模型决策。

**P2 统计整形** —— 人眼判断颗粒靠三件事：尺寸/频谱、密度响应、通道相关，当前三项都不对。全部可用解析公式修复，零资产、零架构改动。

**P3′ 异步 CPU 颗粒场** —— 颗粒是静态场，不需要每帧重算。用线程池在参数/缩放变化时生成颗粒场纹理，显示着色器采样；平移复用缓存。复用 DIR 已有的异步 worker 模式。

**P1b 导出末端 GPU 化 + ICC 修复** —— 导出默认走 GPU 渲染，但末端仍在 CPU 上逐像素做色彩空间转换（colour-science），且转换失败时会静默返回 sRGB 像素却仍嵌入目标空间 ICC，产生"像素与标签不匹配"的偏色文件。这段是导出链路里唯一还没被 GPU 化的逐像素计算，收益与风险都明确。

**P4′ CPU 真 MC** —— 把统计近似换成真抽样（泊松-二项 + 子层 + Jarvis 云），获得自然偏度与团簇形状。numba 多线程把 64 MP 压到 1 s 内。

### P1｜统一实现 + 尺寸保护（1 人日）`low` ✅ 已完成

**结果（2026-10-27，v0.4.47 / Build 209）**：28 项验收全过。

**已核实的根因**：预览与导出的幅度差不是"某个系数写错"，而是**两套实现各自定义了振幅**。着色器噪声流（`smooth_cloud_noise`）的标准差是 **0.1443**（smoothstep 双线性插值把均匀晶格的 0.2887 压低了），三层混合后 `layer_grain` 的 std 约 **0.203**；CPU 导出则把噪声归一化到 1 再乘 0.5，得到约 **0.507**。两者相差 2.5×，同一个滑块位置的导出成片比屏幕重得多。

**做法：把"多少"和"哪里"全部收进 `core/grain_model.py`**
- 八度结构（频率 `0.75/0.45/0.22`、增益 `2.0/1.8/1.6`）、权重曲线（由柔化滑块算出）、层相关混合公式、密度响应、强度链路常数、`log10(e)` 全部集中一处；
- `expected_layer_std()` 解析给出"给定胶卷/柔化/相关度下 `layer_grain` 应有的标准差"，作为两侧共同的振幅定义（不引入额外增益）；
- 着色器改为接收 `u_grain_w_fine / w_cloud / w_mottle` 三个 uniform，不再自己算权重（`blur_t` 已从着色器消失）；**预览振幅保持原样**，修的是导出侧；
- CPU 导出改为调用 `grain_model.synthesize_layer_grain()`，与着色器同结构（三个八度、同一张权重表、同一混合公式）。CPU 侧用高斯模糊近似值噪声，每个八度**重新归一化到 `VALUE_NOISE_STD`**（着色器值噪声的固有标准差），并去掉原来的 `×0.5`。这样"谱形可以不同、振幅必须相同"由构造保证。

**σ 下限保护**：`octave_sigmas()` 给最细八度设 `MIN_OCTAVE_SIGMA_PX = 0.35` 下限。此前导出长边 3000 px 时单 σ 降到 0.31 px，代码里 `if sigma > 0.35` 的分支直接跳过模糊 → 退化成白噪声；现在 3000 px 下三个八度的 σ 是 `(0.35, 0.455, 0.931)`，全部仍有真实模糊。

**验收（实测）**
| 项 | 结果 |
|---|---|
| `layer_grain` std vs 解析预测 | 三档尺寸相对误差均 **0.3%** |
| 导出/预览振幅比 | **1.0012**（旧导出于此差 2.5×） |
| 3000 px 相对 100% 振幅比 | **1.0027** |
| 3000 px 八度 σ | `(0.35, 0.455, 0.931)`，无跳过 |
| 径向 PSD 斜率 | −1.25 / −0.92 / −0.42（均为结构化噪声，非白噪声） |
| `grain=0` | 输出与输入 **逐位相同**（diff = 0） |
| 着色器与模块一致性 | 八度增益 2/2 命中、9 个字面量逐一比对、3 个 uniform 在位、无额外增益、`blur_t` 已移除 |

**脚本**：`tools/grain_parity.py`（28 项）。

**顺带清理**：`export_image` 里从未被使用的 `grain_scale` 局部变量与 `grain_scale_px` 导入。

**未做（属 P2）**：振幅已对齐，但两侧**频谱形状仍不同**（GPU 是值噪声，CPU 是高斯模糊）。PSD 斜率在 100%/80%/3000px 分别为 −1.25/−0.92/−0.42，物理目标是 −0.8，这一步留给 P2 的统计整形。

### P1b｜导出末端色彩空间 + ICC 修复（1 人日）`mid` ✅ 已完成

**结果（2026-10-27，v0.4.46 / Build 208）**：全部验收项通过，但**实现方式与原计划不同**，差异与理由见下。

**背景（已核实）**
- 导出默认是 GPU 渲染（`render_offscreen` FBO → `glReadPixels`），但 `save_encoded_image` 里仍在 CPU 上用 colour-science 逐像素做色彩空间转换；
- `convert_image_colorspace` 的 `except` 分支返回裁剪后的 sRGB 像素，随后 `get_icc_profile_bytes(colorspace)` 仍嵌入目标空间 ICC → **像素与标签不匹配**（如 sRGB 像素标 P3），偏色且难以定位；
- 同处还有一处无害笔误：`colorspace.lower() not in ("srgb", "srgb")` 重复项。

**计划外的两个发现**
1. **colour-science 的实际成本比估算差 15–20 倍**：原以为 64 MP 非 sRGB 末端 0.5–2 s，实测 Rec.2020 **30.3 s**、ProPhoto **37.8 s**。这不是"顺手优化"，而是单靠自己就把 10 s 导出预算打穿的缺陷。
2. **ProPhoto RGB 存在真实的偏色缺陷**：`XYZ_to_RGB(xyz, 'ProPhoto RGB')` 的输入 XYZ 是 D65，却没做 D65→D50 色适应，等于把 D65 数据当 D50 解释。中性白被映射到 `0.968 / 1.013 / 1.320`，全图平均偏 4.0/255、最大 36.6/255。修复后白色不一致度 0.009/255。P3 / Adobe / Rec.2020 三条路径原本正确。

**与原计划的偏离：没有改用着色器，改为 CPU 多线程内核**
原计划是把转换搬进导出着色器。实际放弃，理由：
- 着色器省不掉 `glReadPixels` 回读（PIL / imagecodecs 都要 CPU 像素），转换本身仍是一次内存带宽受限的全图遍历；
- 着色器方案要么与 CPU 导出路径形成**两份实现**（本项目在 DIR 上已吃过"双实现必然不一致"的苦头），要么 CPU 路径就没有快路径；
- 实测 CPU 内核已达 205 ms / 64 MP，着色器的边际收益约 0.2 s，对 10 s 预算无意义，却要动所有预览共用的主着色器（回归风险）。
- 因此改为**单实现 + 双精度档**：`core/colorspace.py` 一个解析器 + numba 内核（8-bit 走查表快路径，16/32-bit 走精确幂函数）。GPU 与 CPU 两条导出链共用它，一致性由构造保证。

**任务（实际完成）**
1. 新增 `core/colorspace.py`：`resolve()` 同时决定「像素转去哪个空间」与「嵌入哪个 ICC」，两者不可能再分歧；
2. numba 多线程内核，8-bit 用 16-bit 解码表 + 32768 节点编码表线性插值，16/32-bit 用精确幂函数；纯 numpy 版本作为 numba 缺失时的回退（两者逐位一致）；
3. **失败语义修正**：转换不可用 → 降级为 sRGB 像素 + sRGB ICC 并记 warning；EXIF `ColorSpace`(0xA001) 与 JPEG XL CICP 一并改为按**实际**空间取值；
4. 清理重复元组笔误；
5. 主窗口显示后守护线程预热 JIT，首次导出无停顿。

**验收（实测）**
- sRGB 导出：逐像素 diff = 0（走零拷贝旁路，不进入转换函数）；
- 非 sRGB 与 colour-science 参考比对：8-bit 最大偏差 P3 0.002 / Adobe 0.458 / Rec.2020 0.007 LSB，16-bit 全部 0.0000；ProPhoto 对正确参考 0.002 / 0.0000；
- ICC 与像素一致：写盘后回读校验全部 5 个空间 × 8/16-bit；再用 LittleCMS 做 profile→sRGB 回环，P3/Adobe/Rec.2020 最大 1/255、ProPhoto 8-bit 11/255（对照：用 colour-science 直接写的"理想" ProPhoto 文件回环 28/255，故 11 是 8-bit 存储量化，不是错标）；
- 64 MP 非 sRGB 末端耗时：**8-bit 205 ms、16-bit 870 ms**（原 30–38 s）；
- 注入异常：降级为 sRGB 像素 + sRGB ICC，不产生错标签文件；
- 脚本：`tools/export_colorspace_check.py`（41 项）、端到端文件校验 18 项。

**未做（明确留手）**
- 量化/抖动没有搬到着色器：8-bit 量化本来就在 RGBA8 FBO 里由硬件完成，抖动是观感决策而非正确性问题，未纳入本次。若后续要做抖动，应作为独立可开关项，否则会打破"sRGB 导出逐位不变"的验收基线。

### P2｜统计整形（1.5 人日）`low` ✅ 已完成

**结果（2026-10-27，v0.4.49 / Build 211）**：6 项统计验收 + 33 项 P1/一致性验收全过；A/B 图见 `docs/grain-ab.png`。

1. **密度响应换成标定的钟形曲线**：在负片光学密度域 `D = -log10(lin)`，峰 `D=0.8382`、趾宽 `0.6149`、肩宽 `1.4884`（P0 拟合）。与参考曲线最大误差 **4.8%**。曲线与增益全部走 uniform，预览/导出不可能各算一套。
2. **频谱**：八度保持独立种子；**门禁改为自相关半宽**（参考 1.81 px），实测 **1.816 px**。
3. **通道相关由参数推出**：新增 `rho_for_target_correlation()`，从"三通道平均相关"反解 mix 系数，观测量不再随层权重漂移；实测 **0.788**（目标 0.79）。

**振幅口径已改为物理口径**（详见第 13 节）：`amplitude = long_edge / 5857`。100% 导出不变，80% 变淡 20%，3000 px 变淡 49%。P1 判据同步改为「σ 比 = 长边比」，实测 0.8011 / 0.5139。

**判据修正（重要）**：原目标「PSD 斜率 −0.8」经 P0 改为「−2.0」，而**两者都不可靠**——该估计在 192 px 补丁读 −2.01、384 px 读 −1.74；且单一斜率无法区分「白噪声+陡峭拐点」与「三个宽高斯之和」。按它调参会得到统计达标但观感明显偏粗的结果（自相关半宽 2.04 vs 1.81）。现 PSD 降为参考信息（当前 −1.36 vs 参考 −1.76），门禁换成自相关宽度。完整复盘见 `docs/grain-calibration.md` 第 7 节。

**已知残差**：中频能量偏多（A/B 中略柔、带云状调制）。这是 v0.4.44 刻意加入的染料云团特征，与纯粒子模型本就不同；是否为了贴合参考而削掉，属审美决定。
### P3′｜异步 CPU 颗粒场（1.5 人日）`low` ⛔ 实测不可行，未实施

**结论（2026-10-27，v0.4.50）**：按原设计（CPU 生成颗粒场 → R16F 上传 → 着色器采样）在预算内无法实现，**已停止**。

实测 CPU 合成一份 `layer_grain` 场的耗时（`scratch/p3_probe1.py`）：

| 尺寸 | 优化前 | 优化后 | 计划预算 |
|---|---|---|---|
| 1080p 视口 | 474 ms | 281 ms | — |
| 4K 视口 | **1975 ms** | **1165 ms** | **≤ 300 ms** |
| 24 MP 导出 | 8752 ms | 6115 ms | 0.2–0.35 s |
| 64 MP 导出 | 16210 ms | 8976 ms | ≤ 3 s |

即使把随机数生成换成 numba（232 → 45 ms / 4K RGB）并去掉每八度的 `std()` 归约（72 ms/八度，改为解析高斯方差因子），4K 仍需 1.1 s，超出预算 3.9 倍。剩余成本是 5 个八度各自的模糊与合并pass，属内存带宽受限，numpy/cv2 层面已无明显余地。

**计划的 40–110 ms 估计从未被测量过**，实测差了 10–27 倍。这与 P0 的教训相同：先测再建。

**建议**：预览颗粒继续留在着色器（当前已通过 uniform 与 CPU 端共享振幅/统计参数，P1/P2 已保证一致），不引入 CPU 颗粒场。

## 7. 顺序逻辑

```
P0 测量 → P1 修错 → P1b 导出末端修错 → P2 改观感 →（人工 A/B）→ P3′ 异步化 → P4′ 上物理
```

1. 先测量：没有目标值就无法验收。
2. 再修确定性缺陷：不需要决策、风险最低、用户立刻可见（P1 颗粒一致性、P1b 导出偏色）。
3. 再改观感：纯公式即可拿到约 80% 的收益。
4. 最后做架构与物理：前者是手段，后者是锦上添花。

## 12. low 档执行约定

全线 `low` 的核心风险不是"做得差"，而是 **`low` 倾向于相信第一个猜测就动手**。因此把判断前移到文档里，让执行只需照做。

**执行方式**
1. 每阶段先读本节 + 该阶段小节，**逐条照做**，不自创方案。
2. 每完成一条，立刻运行对应验收脚本；失败就按"已知失败模式"表处理，**不做开放式排查**。
3. 不在阶段内做计划外的"顺手优化"。发现新问题 → 记进第 13 节，继续当前阶段。
4. 每阶段结束必须让验收脚本全绿才算完成；红着不进入下一阶段。

**验收脚本先行**
写实现之前先把验收脚本写出来（或至少明确它的输出格式）。`low` 模式下脚本是唯一的"裁判"，没有脚本就等于没有验收。

**已知失败模式 → 预定动作**

| 症状 | 预定动作（不要自由发挥） |
|---|---|
| 数值差略超阈值（< 3×） | 先查量纲/归一化（σ 按密度还是按像素、PSD 是否去窗），再查是否用了 uint8 中间量 |
| 数值差远超阈值（> 3×） | 停手，记录实测值到第 13 节，**不要猜**；等确认 |
| 预览与导出不一致 | 优先查是否走了两条代码路径；本计划的整个前提是"单一实现" |
| 耗时超标 | 先测是否包含 JIT/首次分配；再查是否多余的全图拷贝（P1b 就在这里栽过） |
| 观感"说不清哪里不对" | 出三联 A/B 图，交人工判断，不自行改参数 |
| 测试脚本自身报错 | 先确认是脚本 bug 还是实现 bug——用一段最小用例隔离 |

**何时允许破例升档**
只有一种情况：验收连续两轮红、且按上表动作都无效。此时停下来汇报，由人工决定是升档还是改计划——**不要自动升档烧钱**。

## 14. 待办：每胶卷密度曲线接线（**v0.5.0 已用另一条路线实施，见 §15**）

> 本节保留原始设想作为对照。实施时没有走"用曲线把 logE 换成 D、再套全局钟形"，理由见 §15。

**为什么值得做**：档案里 `data.log_exposure`（256 点）+ `data.density_curves` 是**无歧义的每胶卷 H&D 曲线**，实测跨胶卷差异极大——同一 logE=-2 处密度从 0 跨到 3.85。而我们现在对所有 53 支胶卷套用**同一条**全局「颗粒度 vs 密度」曲线，仅靠 size/strength/layer_weights 区分。

正确做法是：先用该胶卷自己的密度曲线把局部曝光换成局部密度 `D = f_stock(logE)`，再套全局的颗粒度-密度钟形。这样每支胶卷的颗粒随明暗变化自然不同，而钟形本身仍是 P0 标定的同一条。

**为什么没做**：
- `crystal_grain.density_profile` / `density_law` 这两个字段在 spektrafilm 与我们的代码里都**没有消费者、也没有文档**，语义未知，不应猜；
- 权威数据是 `density_curves`，但它需要按胶卷类型区分（负片/反转片/黑白，反转片的密度随曝光**下降**）；
- 着色器端需要一张按胶卷烘焙的 1D 查找纹理（`logE → D`），并在换胶卷时重传；

粗估 **1 人日**（不是原先估的半天）。收益是"不同胶卷的颗粒确实不同"，这是目前离物理参考最真实的一处差距——比真 MC 值得做得多（真 MC 的差异只值 2 个可拟合标量，代价却是 5–70 倍耗时，见第 13 节）。

## 15. P5｜每胶卷密度律接线（0.5.0 已完成）

### 实际走的路线（与 §14 设想不同）

§14 设想是：先用每支自己的 H&D 曲线把 logE 换成 D，再套 P0 的全局钟形。

实施时改成：**直接用 fotufilm 档案里逐支声明的 `density_law`（四种）与 `density_profile`/`reversal_profile`/`fog_density`/`granularity_read_density`，在渲染器自己的 D 空间里算颗粒度**，烘焙成 512×1 RGB 表给两个渲染器共用。

换路线的三个理由：

1. **全局钟形本来就是近似**：它只是 P0 对**一支参考胶卷**（Portra-400 类）的拟合。厂商档案已经逐支给了"颗粒度 vs 密度"的律，直接用它比"曲线→D→同一条钟形"少一层映射误差。
2. **§14 路线等于再实现一套物理**：把 256 点 H&D 曲线在着色器里复现（还要处理反转片反向、中灰 logE 平移）是第二套曲线求值逻辑，与"单一真源"的原则冲突。LUT 只要一张表。
3. **归一化锚点让两种路线可比**：每支律在自己的读数密度处归一，`response(anchor) == DENS_GAIN`，所以换律不会偷偷改变颗粒强度；旧钟形在 D=1.0 处是 0.7157，差 0.6%（见下）。

### 锚点归一化（这一节是核心，改动前必读）

```
anchor = granularity_read_density == "gross" ? (1 − dMin) : 1
        再 clamp 到 [0.05, 0.9] × (dMax − dMin)
here   = max(D, 0) + fog_density            # D = −log10(clamp(lin, 1e-4, 1))
mod(D) = sqrt( V(here) / V(anchor) )        # V = 四种律之一
response(D) = DENS_GAIN · mod(D) · （越过 dMax 时滚降到 0）
```

`DENS_GAIN = 0.72` 仍是唯一幅度常数。没有这一步，四种律的量纲不可比（silver 在 D=2.2 处会到锚点的 2.5 倍，而 dyeCloud 只有 0.25 倍）。
